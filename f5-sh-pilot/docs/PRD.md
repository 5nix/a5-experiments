# PRD｜SH 静态高负荷模拟桌面实验系统

> **版本**：1.0（开发启动版）  
> **编制日期**：2026-10-18  
> **当前目标**：2026-10-19 支持 4 名被试的 Pilot；后续支持正式实验。  
> **实施角色**：本文定义产品行为、实验约束、输入输出与验收；**具体技术栈、软件架构细节和部署方案由开发 Agent 决定**。  
> **适用范围**：SH（静态高负荷）场景；SL/MH/ML 不纳入本轮开发。  
> **材料状态**：任务文本、数值、图片和刺激文案仍可修订，必须数据驱动，不视为不可变更的源代码。

## 0. 开发 Agent 首先阅读

建设一个**具有现代 Windows 办公桌面熟悉感、但实验交互受控**的任务系统。被试按预置配置，顺序完成 SH01—SH05 共 5 组任务，每组含 U1、U2 两个单元；程序在 U1 指定展开事件或 U2 开始时自动向雷鸟智能眼镜发送预设消息；在每组任务后自动完成消息理解题、4 项评价量表、3 分钟休息；实验员可在后台查看进度、记录访谈和异常，最终导出完整实验数据。

**几条不能擅自改变的规则：**

1. 每名被试的实验条件**已经事先分配好**。程序只导入并执行配置，不负责随机化、分组算法、20/40 人平衡设计，也不要求主试每轮手动选消息。
2. U1 **提交后直接自动进入 U2**，没有额外的“进入下一题”按钮，也不加入假加载、过渡页或人为延迟。
3. **T0**：U1 首次实际展示指定补充信息的事件 **E** 触发消息；**T1**：U2 内容实际呈现时自动触发消息发送；**NONE**：不发送消息。消息发送不阻塞主任务。
4. 消息由**雷鸟智能眼镜**显示，持续 **8.5 秒**后自动消失；期间被试可以始终正常操作桌面。**不要在桌面同步弹出实验消息**。
5. 眼镜通信接口由雷鸟开发同学另行提供；现在先设计可替换适配接口与 Mock，**不得为了等待硬件接口阻塞主任务开发**。
6. **有消息的任务组**：U2 提交 → 对应消息理解题（自动判分、不展示正确答案）→ 4 项 1–7 分评价 → 3 分钟休息 → 下一组。**无消息组**：U2 提交 → 跳过消息题和评价 → 3 分钟休息 → 下一组。
7. 原材料中的错字、矛盾、裁切内容**不要偷偷修正、不要自行编造**；保留内容来源并做可修订的数据层，具体问题见 §12。

### 项目成功的标准

一个实验员通过导入被试配置并启动实验，就能让被试从情景导入完成到 SH05 结束；不需要实验员手工挑选 5 组任务各自的消息。任务答题、消息触发、问卷、计时、异常均可追溯；即使尚无真实眼镜接口，也能用 Mock 完成同样的完整流程。正式硬件接入时只替换适配器，不应改主任务业务逻辑。

## 2. 本期范围 / 非目标

### 必做（Pilot 最小完整闭环）

- 现代 Windows 风格的模拟桌面壳，以及承载任务的办公窗口。
- 情景导入页；5 张任务说明卡；10 个任务单元；结束页。
- U1 的基础表格、主动展开的第二份资料/规则、答案编辑和提交；U2 的更新资料、答案编辑与提交。
- 根据被试配置选择 N/A/T0/T1/NONE，自动触发消息；Mock 可见地验证发送行为。
- 10 单元评分、理解题判分、4 条主观量表、统一 3 分钟休息流程。
- 实验员侧被试选择/启动、进度监视、异常与访谈备注、数据导出。
- 完整事件日志、原始答案、结果汇总与数据恢复能力。

### 不做或暂不强求

- 真实 Windows 操作系统、完整文件管理器、Office、邮件、会议或打印功能；情景提及这些事务不代表被试需要真的操作。
- 自主决定被试条件、重新平衡试次、自动随机抽样。
- 在电脑上模拟眼镜消息弹窗作为正式介入刺激（Mock 测试界面仅限调试模式）。
- 上线复杂的账号系统、研究平台、多机构协作或实时分析仪表盘。
- 将实验设计用的 NASA-TLX 强行加入正式被试流程：PDF 只提到“已准备好用于检查负荷”，**没有明确规定其最终在线收集位置**。可以保留问卷扩展点，但默认正式流程只包含已确认的理解题和 4 项评价。
- 语音录制、录音转写；访谈由实验员线下进行，后台只需手动记录。

## 3. 角色与使用流程

**被试端**：看见 Windows 风格办公桌面和受控任务窗口，阅读任务、按要求核对表格、填写答案并提交；在眼镜上接收一次或零次消息，正常继续电脑任务；完成任务组后做问卷并休息。

**实验员端**：导入全部被试预置配置，选择当前被试并启动/结束实验，检查眼镜设备状态，观察记录是否正常；必要时填写异常备注或访谈记录、导出数据。主试**不需要逐个任务选择 N/A、T0/T1**。

**开发者/调试端**：可以开启 Mock 显示发送请求、模拟延迟与失败、查看原始事件、复现特定被试配置。任何调试信息及标准答案不得出现在正式被试端。

## 4. 核心被试流程与状态机

```text
导入/加载已分配配置（实验员）
  → 创建 session → 情景导入 INTRO
  → SH01 说明卡 → SH01_U1 → [提交即自动切换] → SH01_U2
  → [若有消息：消息理解题 → 4项量表；若 NONE：直接跳过]
  → 休息 180秒 → 继续
  → SH02 说明卡 → SH02_U1 → SH02_U2 → 理解题/量表(按条件) → 休息
  → SH03 说明卡 → SH03_U1 → SH03_U2 → 理解题/量表(按条件) → 休息
  → SH04 说明卡 → SH04_U1 → SH04_U2 → 理解题/量表(按条件) → 休息
  → SH05 说明卡 → SH05_U1 → SH05_U2 → 理解题/量表(按条件)
  → EXPERIMENT_COMPLETED → 实验员现场访谈/备注 → 导出
```

**说明：**原 PDF 要求每组后休息 3 分钟；最后一组实验已结束，默认无须再等待 3 分钟才进入完成页。每组休息达到 180 秒后出现可点击的“继续”，防止无人值守时直接自动推进。如果实验员另有口头核对要求，可以在后台记录结果，但不将其假定为被试的额外作答题。

**U1 到 U2 的严格行为：**

- 被试点击 U1“提交” → 立即保存答案快照并判分 → 自动切 U2 → U2 实际可见时记 `u2_displayed`。
- 若当前组是 T1，在 U2 显示的**同一状态转换**中向眼镜适配器发起发送，不使用固定延迟、不额外等待或增加按钮；设备传输造成的自然差异单独记录。
- 若当前组是 T0，眼镜消息应早在 U1 的 E 时机发送，切 U2 时不再重复。
- 若当前组是 NONE，不发送消息，但 U2 跳转行为一致。
- 页面加载应尽量稳定、快速；不人为制造 T1 专用加载效果。**不要为了制造“自然感”重新加入已经否决的假加载。**
- U2 提交后自动进入本组结果收集环节；不给被试展示主任务对错。

**边界情形**：被试从未展开 U1 资料就提交时，不得把 T0 偷换为提交时或 U2 时触发；如当前协议无额外约定，记录 `E_not_observed` / `message_not_triggered` 以供 Pilot 复核。页面可提示任务包含“查看资料”的操作，但不额外增添强制步骤，除非任务题干本来明确要求。

## 5. 模拟桌面视觉与交互要求

### 5.1 视觉

以现代 Windows 常见使用经验为参照：简洁桌面壁纸/背景、底部任务栏、办公软件式顶栏和窗口、可辨认的按钮、输入框和数据表格。目标是**用户熟悉、能专注任务**，非像素级复刻 Windows 或 Office；不需要开发完整窗口管理器，也不应堆叠花哨动效。

### 5.2 交互

- 整个实验只允许进入流程定义的页面；任务窗口布局一致，数据和题型随配置切换。
- U1 初始只显示基础资料、题干和答题区。被试点击“查看方案筹备日期表”等动作，才显示对应补充资料；首次实际显示定义为 **E**。重复点击/折叠/展开不重复记录 E，但操作日志可记录。
- U2 显示该单元的完整/更新资料，不强行复用 U1 中已展开的同一表格表现形式。
- 输入控件与题型相匹配：多选、单选、数值、时间、人员选择；不提供自动求解或实时判分提示。
- 支持正常鼠标和键盘操作、清除与修改答案；提交时保存原样答案与规范化答案。
- 原稿存在“漏答记0”，所以**不应强制所有字段答完才允许提交**。非法输入可提示“格式无法识别”，与“填错答案”区分；具体合法格式由题型配置控制。
- 选项“没有合格方案”“无人可纳入”与普通候选互斥。
- 不让被试看见实验条件、标准答案、E/F、调试计时、设备调用和日志。

## 6. 五组任务内容规范（文字、图片、数值外部配置）

开发 Agent 应阅读 PDF 第 1—11 页以及用户补充的清晰原表格，逐单元还原**被试看见的任务内容**。本节是实现索引，**不代替源材料**。

| 组 | 说明卡主题 | U1 题型与补充信息（首次展开 E） | U2 题型 | 当前文档标准答案 / 核验重点 |
|---|---|---|---|---|
| **SH01** | 方案筛选/线上评审 | 基础报价、人数表 + 展开筹备日期表；合格方案多选 | 4 项最终费用（万元，2 位小数）+ 合格方案多选 | U1 `{A,B}`；U2 `A 5.04, B 4.89, C 4.92, D 4.88` 与 `{B,D}` |
| **SH02** | 场地准备排程/清单打印 | 工序时长 + 展开人员可用时间；3 个时间填空及能否按时 | 更新调试及验收限制，重新安排时间 | U1 `9:45/10:45/11:15/能`；U2 `9:45/11:00/11:45/不能` |
| **SH03** | 参与资格/会议资料 | 参加时间与资料 + 展开确认状态；总人数和缺口 | 人员状态变化 + 按顺序选替补 + 总人数/缺口 | U1 `20/4`；U2 `{王帆,赵禾}/23/1` |
| **SH04** | 工作人员排班/展板 | 资格、岗位时间 + 展开到岗时间；3 岗选不同人员 | 缺席、到岗变化、新增支援后重新排班 | **按规则验证可行解**，不可照抄 PDF 的矛盾示例；见 §7 |
| **SH05** | 物料清点/交通 | 库存、损坏数 + 展开配套规则；可用与缺口共 6 个数值 | 补货方案单选 + 2 个剩余量 | U1 `26/4, 32/0, 44/7`；U2 `D/1/3` |

### 6.1 显示内容与判分规则的数据模型

每个单元建议至少配置：`unit_id`、`card_text` / `instruction_text`、`assets[]`、`base_tables[]`、`reveal{button_label,content}`、`form_fields[]`、`submit_label`、`scoring_rule`、`source_ref`、`content_version`。详细表格可以是 JSON 行列数据，也可以有配套图片作为原始视觉资产，但**不得把“标准答案”文字连同任务说明一起渲染给被试**。

建议所有内容都有稳定 ID，文案随时可调整而不影响 session 与导出数据字段；每次实验 session 都需保存使用的**内容快照/版本号**，避免正式实验期间修改题干后无法追溯历史被试看见的内容。

### 6.2 任务说明卡与事件有关的情景信息

卡片内包含业务发生时间（例如 SH01 11 月 6 日 10:00、SH05 11 月 19 日 15:30），这些是**虚拟情景背景**；不可误用于真实事件计时。SH01 阅读卡后原稿提到实验员口头核对理解，这一操作由现场研究者负责，若记录则写入实验员备注，不默认向被试增加程序选择题。

## 7. 任务判分与格式化

### 7.1 通用规则

- 10 个主任务单元分别评分。原文主要采用**整体完全一致记 1，否则 0**（包括漏答、错答），不擅自增加部分分。
- 多选比对**集合**，不依赖点击顺序。单选取一个值。人数、物料数按整数比较。
- 时间规范化为日内分钟，`9:45` 与 `09:45` 视为同一答案。
- 金额以“万元精确到 0.01”的十进制形式比较，避免浮点误差；按照题目要求保留两位小数。
- 作答最终提交时判分；所有编辑过程独立记录，正确答案不能提前泄露。
- **不要误把“答案是否正确”与“允许提交”混为一谈。** 提交错题仍应正常进入下一单元，并获得 0 分。

### 7.2 SH04 特殊约束判分

三个岗位各分配恰好一人；人员具备该岗位资格；到岗时间不晚于该岗位开始时刻；同一人不许重复；U2 还需正确应用缺席、到岗变更、新援人员条件。满足所有约束即 1 分，不满足为 0。不能硬编码某一组三个人名为唯一标准答案。

PDF 的 SH04 U1“标准答案”写的是岗位开始时间，而非人名；SH04 U2 示例把许宁同时安排两个岗位。**保留矛盾为数据审计提示，不应以错误示例作为运行时判分依据。** 部分 U1 到岗时间被 PDF 裁切，须在补充原表到位后才能对该单元完整验证。

### 7.3 SH05 的特殊事件 F

SH05 U1 在原 PDF 明确要求记录“首次有效提交时记 F”。**有效提交与答案正确并非必然相同概念**。实现时至少区分 `first_submit_attempt`、`first_submit_accepted`、`first_submit_complete`、`first_submit_correct`（可从原始数据派生）；在未收到更具体实验定义前，将原稿 F 对应哪一种标记为可配置语义，**默认不用于本轮 T0/T1 的消息触发**。SH05 U1 仍有独立的资料展开 E。

## 8. 实验消息与雷鸟接口

### 8.1 消息类型及条件

| 条件 | 内容 | 发送时机 | 被试问卷 |
|---|---|---|---|
| `N-T0` | 通知型消息 Nxx | 当前 U1 的 E | 有 |
| `N-T1` | 通知型消息 Nxx | 当前 U2 实际显示时 | 有 |
| `A-T0` | AI 主动服务型消息 Axx | 当前 U1 的 E | 有 |
| `A-T1` | AI 主动服务型消息 Axx | 当前 U2 实际显示时 | 有 |
| `NONE` | 无消息 | 不发送 | 跳过消息理解题及4项评价 |

- 每名被试 5 个任务组中，**按现有版本样例**是 4 次消息、1 次无消息；实际只执行导入的预置配置，程序不自行重排。
- 一组任务最多发送当前配置指定的**一条**消息。任意展开、重复渲染、刷新或恢复不得导致同一消息发送两次。
- 消息持续 `8500ms` 后自动消失；**持续时间由眼镜端还是上位机端控制，等真实接口确认**。程序需要把预期 `8500ms` 作为请求/元数据配置，并尽可能记录真实消失情况。
- 消息期间主任务不暂停、不遮挡、不锁定；提交与切换照常进行，不要等待眼镜返回才继续 U2。
- “通知型/AI主动型”是消息**预编写的刺激类别**，本期不要求调用生成式 AI 实时生成文本。

### 8.2 雷鸟适配器（技术实现可由 Agent 自定）

对实验调度器提供稳定能力契约：连接/状态检查、发送单条消息（包含唯一请求 ID、消息内容和期望展示时长）、显示成功反馈（**如 SDK 支持**）、失败/断连报告、清除消息（**如 SDK 支持**）。具体接口形态可以是 HTTP、WebSocket、本地进程调用或 SDK 封装，由雷鸟参考实现决定。

初期必须实现 `MockGlassesAdapter`：日志显示预计发送的消息和发送时刻，可模拟成功、延迟、设备断连、未回执。Mock 的“显示成功”仅是模拟事件，导出时标记 `source=mock`，**绝不可与真实眼镜显示确认混写**。

建议传输请求最少包括 `session_id`、`participant_id`、`stage_id`、`message_id`、`request_id`、`text`、`duration_ms=8500`，但具体协议无需拘泥于这些字段名称。

### 8.3 发出命令与实际看到不可混为一谈

必须分别记下：任务触发时刻 `t_event`（E 或 U2 显示）、命令提交时刻 `t_send`、接口返回/设备确认 `t_ack`（若有）、眼镜实际显示 `t_display`（**仅在设备能报告时**）、消失时刻 `t_hide`（若有）。若真实设备只有“发送成功”，不可将它标记成“实际显示”。导出中应提供 `display_time_source`（`device_reported` / `estimated` / `unavailable` / `mock` 等）。

### 8.4 异常处理

发生发送失败、断连、超过显示时机、无显示回执时：**主任务不中断**，事件日志记录失败原因与可用时间戳，实验员后台清晰提示当前异常、允许填写备注。不要悄悄重发，以免造成双消息刺激；如确需重发，须作为实验员明确的人工干预并记录尝试次数和实验偏差。未知实际呈现时刻保持 `null`，不填 0、不伪造。

## 9. 实验配置导入（不是实验条件分配功能）

### 9.1 要求

系统需能批量读取被试已分配配置，每一名被试预先列出 SH01—SH05 对应的消息类别、消息 ID、时机。主试启动该被试时，程序自动读取。人数可为 4、20、40 或更多，**不把任何总人数作为代码限制**。当前使用原 20 人分配表进行测试。

参考 JSON（**仅为协议示例；不是要求按此文件格式手工重新安排被试**）：

```json
{
  "experiment_id": "SH-PILOT",
  "schema_version": "1.0",
  "participants": [
    {
      "participant_id": "001",
      "version_label": "V1",
      "stages": [
        {"stage_id": "SH01", "condition": "N-T0", "message_id": "N01"},
        {"stage_id": "SH02", "condition": "N-T1", "message_id": "N02"},
        {"stage_id": "SH03", "condition": "A-T0", "message_id": "A03"},
        {"stage_id": "SH04", "condition": "A-T1", "message_id": "A04"},
        {"stage_id": "SH05", "condition": "NONE", "message_id": null}
      ]
    }
  ]
}
```

Agent 可优先采用 JSON 导入；若 Excel/CSV 解析很方便，可提供直接导入，但**不强制增加一个任务分配编辑器**。要求导入校验并反馈：被试 ID 重复、任务缺失/重复、NONE 却绑定消息、消息 ID 与任务不匹配、找不到刺激文案或理解题、条件值非法；不自动生成“正确”的替代分配。

**已知原始分配表问题**：V5 的 SH02 单元写成 `N01-T0`，按其他数据命名习惯疑似应为 `N02-T0`。程序应提示“SH02 使用 N01 不匹配”，**不擅自静默改为 N02**。此问题不妨碍使用无歧义的其他被试配置跑 Pilot。

### 9.2 被试启动行为

选定/扫描/输入 `participant_id` → 加载预置配置 → 显示该人的 5 组只读任务条件摘要（**仅实验员可见**）→ 开始实验。已经开始的 session 应固定本次配置快照及哈希/版本，后续源表被修改不能回写影响已有数据。

## 10. 问卷、休息、结束与访谈

### 10.1 消息理解题

Excel「文案呈现与问答表」给出 SH01—SH05 的 N/A 消息、理解题、A/B/C 选项和正确答案，按本被试、本组实际消息 ID 加载。单题单选，选择 C“没看到或不确定”也应允许。提交后自动判断正确/错误并保存，**不展示对错和标准答案**。

**内容冲突提醒**：SH02 的 A02 当前消息是“建议前往三楼自助打印区打印清单”，但所配理解题问“提交清单前先做什么”，正确答案“预览打印版式”，**信息无法直接从现有消息推出**。系统要按 Excel 当前内容加载并在材料 QA 中标记，不擅自改消息或答案。另有若干刺激候选旧文案，优先将「文案呈现与问答表」作为**本轮默认导入表**，但允许实验设计同学指定修订后的正式版本。

### 10.2 4 项评价量表

每项 1—7 分，独立记录原始数值：

1. **时机合适度**：你觉得这条信息出现的时机合适吗？1 非常不合适，7 非常合适。
2. **打扰感**：这条消息对你刚才做任务的打扰程度有多大？1 完全没有打扰，7 打扰非常大。
3. **完成主任务的努力程度**：因为这条消息，你需要多花多少精力才能继续完成任务？1 完全不需要，7 需要非常多。
4. **帮助程度**：结合情景，这条消息对你处理之后要处理的事情有多大帮助？1 完全没有帮助，7 帮助非常大。

按顺序展示，内容可配置；不显示正确答案或引导性评分反馈。无消息条件下**不展示这四项**。

### 10.3 休息流程

每组结束执行固定 `180s` 休息计时；倒计时结束后开放“继续”，被试或实验员继续到下一组。休息时不呈现实验消息；后台可查看剩余时间。最后一组结束后直接展示完成页，后续访谈由实验员线下进行。

### 10.4 实验员访谈与备注

后台按被试关联自由文本输入框：`访谈记录`、`任务观察笔记`、`设备/流程异常备注`，有保存时间和最后修改时间。建议支持每组追加备注和全实验总结。PDF 最后列出的访谈问题可做后台**提示**，无需在被试界面自动提问，也无需 AI 自动分析。

## 11. 埋点与数据导出（验收关键）

### 11.1 时间原则

- 记录 ISO 8601 墙上时间及 **毫秒级、单调递增的实验相对时间**；跨刷新/恢复应保证同一 session 的时间轴可追踪，必要时记录 time origin / clock offset。
- `*_displayed` 应尽可能对应**页面内容真实可见**的时刻，而非仅仅开始切换状态；消息端遵循 SDK 实际报告能力。
- 统一事件结构包含：`event_id`、`session_id`、`participant_id`、`stage_id`、`unit_id`（适用时）、`condition`、`event_type`、`timestamp_iso`、`elapsed_ms`、`payload`、`content_version`。
- 原始事件**只追加，不覆盖**；聚合数据由事件推导，不以最后一次保存的几个字段取代全过程。
- 浏览器刷新、失焦、重载、人工暂停/恢复、发送失败都记录，不得默默丢失数据。

### 11.2 最低事件清单

| 类别 | 事件 | 语义 |
|---|---|---|
| 导入/说明卡 | `intro_displayed`, `intro_continue`, `card_displayed`, `card_continue` | 阅读开始/继续 |
| 单元 | `unit_displayed`, `answer_changed`, `submit_clicked`, `submission_recorded`, `unit_scored` | 显示、作答变化、提交、判分 |
| 补充资料 | `reveal_clicked`, `reveal_displayed` (**E**) | 点击与首次可见需区分；每个 U1 只记录一次 E |
| 特殊试次 | `submit_accepted_first` / `F_candidate` | SH05 U1，附“有效”的判据版本 |
| 切换 | `unit_transition_started`, `u2_displayed`, `stage_completed` | U1 提交后自动切到 U2 的真实时序 |
| 消息 | `message_scheduled`, `message_send_requested`, `message_send_accepted`, `message_display_confirmed`, `message_hidden`, `message_failed` | 仅记录实际发生或可以证实的状态 |
| 问卷 | `comprehension_displayed`, `comprehension_submitted`, `ratings_displayed`, `ratings_submitted` | 每一页实际显示/提交时间及答卷 |
| 休息/结尾 | `break_started`, `break_completed`, `continue_clicked`, `session_completed` | 休息和实验结束 |
| 异常/管理 | `app_resumed`, `app_blurred`, `admin_intervention`, `device_status_changed`, `note_saved` | 供 Pilot 审计 |

**派生量（至少）**：导入阅读时长、单元完成时间、首次修改/最后修改时刻、E 的首次点击与实际显示时刻、T0 从 E 到设备显示的时间差（仅有设备报告时）、T1 从 U2 显示到设备显示的时间差、发送回执耗时、任务得分、理解题是否正确、4 条评分。

**SH05 F**：单独保留首次被系统接受的提交、首次填完整提交和首次正确提交的证据，别把它们隐式合并；研究者最后选择哪种口径，可从日志重新派生。

### 11.3 导出文件

至少支持 UTF-8（兼容中文）CSV 与 JSON/JSONL，一键按 session 或批量导出：

1. `events.jsonl`：不可变原始事件，最重要的复核底稿。
2. `trials.csv`：每个 U1/U2 一行；含被试、版本、组/单元、条件、页面显示、E/F、首末答、提交、原始答案、标准化答案、得分、所用题库版本。
3. `interventions.csv`：每个预期消息一行；含被试、组、消息 ID、T0/T1、预期时机、E/U2、`t_send`、`t_ack`、`t_display`（如可得）、`t_hide`（如可得）、延迟、状态、设备信息、回执证据。
4. `surveys.csv`：每条消息理解题回答/正确性和4项量表，可一行对应一个已发生的介入；NONE 不产生虚假的问卷记录。
5. `sessions.csv`：被试、配置版本、设备类型、开始/结束/恢复、完成状态、异常数。
6. `notes.csv`：实验员访谈、备注及修改时间。

**数据约束**：未发生、不可测量的时间使用 `null` / 空值，**不能用 0 伪装**；导出的时间差应注明基准事件和单位；Mock 事件与真实设备事件必须可区分。原始数据和聚合结果的行数、关联关系可由 Agent 写自动测试验证。

## 13. Agent 技术方案自由度及必须交付的接口

技术栈、数据库、组件库、部署方式、窗口容器（Web/Electron 等）由开发 Agent 选择；优先**快速、稳定、易本机运行、易调试、易导出**，而不是复杂架构。允许本地优先保存，不强制云服务。至少做到：

- 任务呈现/判分与任务数据解耦；文案、表格、图片可以不改程序直接调整。
- 预置被试配置与实验调度器解耦；无需主试手动重新选择任务条件。
- 眼镜通信通过 Adapter 解耦，可在 Mock 和雷鸟真实实现之间切换。
- 原始事件记录与统计导出解耦，支持实验复核。
- 正式被试模式与开发调试模式分离，确保标准答案、日志、Mock 内容不泄漏到被试界面。

开发 Agent 应在 `ARCHITECTURE.md` 中**简短说明自主选型**：为什么适合单台上位机现场实验、实际部署与启动命令、数据存储位置、导出位置、眼镜适配接入点、失败恢复机制。不要为了技术讨论拖延 Pilot 可用版本。

## 14. 实施优先级与交付里程碑

### M0｜今天：可运行 Pilot 闭环（最高优先）

**目标**：完成导入一个被试配置 → 情景导入 → SH01—SH05 10 单元 → 自动切换 U2 → Mock T0/T1 → 对应理解题 → 4项量表 → 3分钟休息 → 完成 → 导出。确保电脑界面没有显示模拟眼镜通知；Mock 只在调试模式展示。若原始表格未提供齐全，允许在对应项目显式标 `待补充资料`，不能虚构数值并误称验收通过。

### M1｜数据与材料核验

补齐所有来自 PDF/原表格的可见内容、对照判分与体验流程；完成事件日志可靠落盘、重新启动的恢复和完整 CSV/JSONL 导出。对 SH04 的裁切和冲突建立自动 QA，最终实际打通 10 单元正确性验证。

### M2｜雷鸟设备联调

在取得参考接口后接入真实 Adapter；验证命令送达、设备断连、显示回执能力、8.5 秒显示与消失（能测则测）、T0 E→发送、T1 U2→发送时序。不能获得真实 `t_display` 时，日志明确写“不可得”，不要以发送时刻假扮。

### M3｜正式实验稳态

增加所需的异常恢复、自检、配置版本管理及一键完整数据备份。只在有证据时增加更复杂功能。
